# Поиск дублей объявлений — Avito ML Cup 2025

Задача [«Поиск дублей»](https://ods.ai/competitions/avitotechmlchallenge2025_2),
апрель–май 2025: для пары `(base_item_id, cand_item_id)` предсказать вероятность
того, что кандидат — дубль базы.

| | |
|---|---|
| Обучение | 1 879 555 пар |
| Тест | 500 000 пар |
| Доля дублей | 5.6 % |
| Кандидатов на базу | 2.6 в среднем |
| Метрика соревнования | MAP по кандидатам внутри базы |

Данные — [`chuvirla/avito-ml-cup-default-dataset`](https://www.kaggle.com/datasets/chuvirla/avito-ml-cup-default-dataset),
фотографии лежат отдельными наборами:
[`uhtiblya/train-images`](https://www.kaggle.com/datasets/uhtiblya/train-images),
[`uhtiblya/test-images`](https://www.kaggle.com/datasets/uhtiblya/test-images).

---

## Что нашлось в данных

**Тексты обфусцированы.** 71 % кириллических токенов содержат подменённые латинские
буквы: в `Куpткa` латинские `p` и `a`. На сравнение строк это почти не влияет — обе
стороны пары обфусцированы одинаково (+0.0014 PR-AUC на голом Жаккаре), — зато ломает
словарь предобученной модели. Отсюда две разные операции в [`text.py`](src/text.py):
свёртка азбук для сравнения строк и починка гомоглифов перед подачей в трансформер.

**Случайное разбиение течёт.** `group_id` — кластер связанных объявлений, и одно
объявление стоит в нём и как `base`, и как `cand`. При `StratifiedKFold` по строкам 45 %
объявлений валидации (304 051 из 674 800) уже были в обучении, при `GroupKFold` по
`group_id` — 0.4 %. Цена утечки: **0.589 против 0.469 PR-AUC** на одних и тех же признаках.

**Цена `-1` значит «не указана».** Наивный `log1p` даёт минус бесконечность,
стандартизация разносит её по всему признаку, и обучение башен падало в `nan` с первой
эпохи — молча, без ошибки.

**Хеш фотографии бесполезен, а сами фотографии — нет.** `title_image` — 64-символьный
хеш главного фото, и между `base` и `cand` он не совпал **ни разу на 1.88 млн пар**:
перепост пережимает файл заново. Сами изображения стыкуются с парами по этому же хешу —
имя файла равно значению `title_image`. Внутри набора файлы разложены по чанкам, и по
хешу нельзя вычислить, в каком чанке искать, поэтому [`images.py`](src/images.py) строит
индекс «ключ → чанк» одним проходом и хранит его массивом номеров чанков, а не словарём
строк. На 3.15 млн фотографий индекс строится за 73 с и находит 99.9 % ключей.

**MAP на открытых данных вырождена.** На базу приходится 2.6 кандидата, а дубль есть
лишь у 7.4 % баз: случайный скор даёт MAP 0.87, идеальный — 1.0. Настоящий тест
соревнования закрыт и участникам не выдавался, так что сравнивать эти числа с
лидербордом нельзя. Основная метрика здесь — **PR-AUC на парах**: она не вырождается и
чувствительна к дисбалансу 5.6 %.

---

## Решение

Пара описывается признаками сходства, поверх них учится градиентный бустинг. Ни одна
сторона не попадает в модель сама по себе — только сравнение сторон.

* **58 парных признаков** ([`features.py`](src/features.py)) — совпадение и Жаккар
  заголовков и описаний по токенам и символьным n-граммам, containment, общий префикс,
  отношение длин, отдельно Жаккар по числам, заголовок одного внутри описания другого,
  `json_params`, цена, гео, категории.
* **Эмбеддинги `rubert-tiny2`** ([`embeddings.py`](src/embeddings.py)) считаются один раз
  на уникальный текст: их 2.66 млн против 3.76 млн сторон пар. Пары адресуют таблицу
  индексами, а не хранят векторы.
* **Двухбашенная контрастная модель** ([`models.py`](src/models.py)) — обучаемая проекция
  над замороженным энкодером. Косинус недообученных эмбеддингов меряет смысловую
  близость, а нужна близость в смысле дубля: два похожих зимних пуховика близки по
  смыслу, но дублями не являются.
* **Сравнение фотографий** ([`images.py`](src/images.py)) — перцептивный хеш ловит
  буквальный перепост, CLIP ловит пересъёмку того же товара с другого ракурса.
* **Кросс-энкодер** ([`cross_encoder.py`](src/cross_encoder.py)) — проверен и в решение
  не вошёл, см. ниже.
* **Валидация** — `GroupKFold` по `group_id` ([`validation.py`](src/validation.py)).

## Результаты

Полный прогон на 1 879 555 парах, Kaggle T4, 5 фолдов `GroupKFold` по `group_id`.

| | PR-AUC | ROC-AUC | MAP |
|---|---|---|---|
| Жаккар заголовков, без обучения | 0.152 | 0.757 | — |
| **это решение, OOF по 5 фолдам** | **0.496** | **0.906** | 0.941 |

По фолдам PR-AUC: 0.477, 0.510, 0.538, 0.461, 0.498.

### Вклад блоков признаков

Абляция на одном фолде, 400 деревьев, всё остальное неизменно:

| Убрано | PR-AUC | Потеря |
|---|---|---|
| ничего | 0.4738 | — |
| `json_params` | 0.4701 | 0.004 |
| эмбеддинги | 0.4686 | 0.005 |
| **сравнение фотографий** | 0.4584 | **0.015** |
| скор башен | 0.4529 | 0.021 |
| эмбеддинги и башни вместе | 0.4513 | 0.023 |
| цена, фото, гео | 0.4506 | 0.023 |
| **текстовое сходство** | 0.4083 | **0.066** |

Основа решения — простое сравнение строк: без него теряется 0.066, больше чем от всего
остального вместе. Обучаемая проекция при этом ценнее сырого косинуса — без башен
теряется 0.021, без эмбеддингов 0.005, — и `two_tower_sim` оказался первым признаком по
вкладу в бустинг с отрывом в 8.6 раза от следующего.

Фотографии дают +0.015, и это оценка снизу: закодировать успели 1.95 млн уникальных
снимков из 3.15 млн, обе фотографии нашлись у 75.5 % пар. Там, где нашлись, косинус CLIP
у дублей 0.773 против 0.711 у не дублей.

Кодирование упирается в бюджет запуска, а посчитанное умирает вместе с ядром, поэтому
таблица эмбеддингов сохраняется на диск вместе с ключами. Подключённая входным набором,
она подхватывается следующим запуском, и кодируются только недостающие строки. Ключи
сопоставляются по именам, а не по позициям: порядок ключей зависит от данных и от запуска
к запуску меняется.

### Кросс-энкодер: проверен и отвергнут

Башни кодируют стороны независимо и сопоставить слово базы со словом кандидата не могут:
«iPhone 11, 256 ГБ» и «iPhone 11, 128 ГБ» дают почти одинаковые векторы. Учебниковый
следующий шаг — кросс-энкодер, обе стороны одной последовательностью через `[SEP]`.
Дообучен `rubert-tiny2` целиком, по одной модели на каждый из пяти фолдов.

| | PR-AUC | ROC-AUC |
|---|---|---|
| бустинг на признаках | **0.496** | 0.906 |
| кросс-энкодер | 0.300 | 0.852 |

Смесь по рангам не помогает, кривая монотонна: при весе бустинга 0.5 выходит 0.420, при
0.8 — 0.465, оптимум — чистый бустинг. Причина в том, что кросс-энкодер видит только
текст, а бустинг — ещё цену, категорию, характеристики и гео. Кандидаты внутри кластера
обычно в одной категории и с похожими описаниями, и различает их как раз то, чего
кросс-энкодер не видит.

Замер узкий: скор кросс-энкодера не подавался бустингу признаком — для этого понадобилась
бы вложенная схема, 25 дообучений вместо пяти, а в бесплатную квоту GPU это не влезает.

### Триплеты вместо пар

Второй заход на ту же башню: вместо парной контрастной функции — triplet margin loss с
отбором трудных негативов по уровням (та же база, та же группа `param2`, соседняя
подкатегория), margin 0.3, четыре негатива на позитив, 12 эпох. Отдельный ноутбук —
[`notebooks/avito-duplicates-triplet.ipynb`](notebooks/avito-duplicates-triplet.ipynb),
код отбора и обучения — [`src/triplets.py`](src/triplets.py).

| Скор башни признаком бустинга | PR-AUC | ROC-AUC |
|---|---|---|
| без башни | 0.4586 | 0.891 |
| парная контрастная | **0.4793** | 0.902 |
| триплетная | 0.4585 | 0.890 |

Сама башня на первом фолде — 0.214 PR-AUC против 0.326 у парной. Негативы оказались
слишком трудными: из 105 тысяч отобранных 30 136 пришли из той же базы, 74 903 — из той же
группы `param2`, а случайных и межкатегорийных ноль. Обучение свелось к ранжированию внутри
кластера, и признак перестал добавлять что-либо поверх остальных 52.

Полный вывод — [`reports/results_triplet.json`](reports/results_triplet.json).

### Что пришлось измерить, чтобы не соврать себе

**Наивный стекинг.** Если подать бустингу предсказания башен, посчитанные на их же
обучающих данных, PR-AUC падает до 0.400 — хуже, чем вовсе без них: на обучении скор
выглядит лучше, чем на новых данных, бустинг на него опирается и разваливается на
валидации. Отсюда вложенная схема — обучающие строки получают скор по внутренним фолдам.

**Ранняя остановка не по той метрике.** LightGBM считает `binary_logloss` в дополнение к
заданной, а колбэк остановки следит за всеми метриками сразу. С `scale_pos_weight`
логлосс деградирует с первых итераций, и обучение обрывалось на втором-третьем дереве:
0.351 вместо 0.5. Метрика задана явно, у колбэка выставлен `first_metric_only`.

Полный вывод прогона — [`reports/results.json`](reports/results.json).

## Воспроизведение

Загрузить [`notebooks/avito-duplicates.ipynb`](notebooks/avito-duplicates.ipynb) на
Kaggle, подключить датасет соревнования и оба набора с фотографиями, включить GPU,
запустить Save & Run All. Ноутбук самодостаточный: ни клонирования репозитория, ни
интернета для кода не нужно. На выходе — `submission.csv`, `results.json` и таблица
эмбеддингов фотографий. Для быстрой проверки есть `QUICK_RUN = True`: одна часть
обучающих данных, без теста.

Если предыдущий запуск не успел закодировать все фотографии, подключите его выход
входным набором — недостающее досчитается, готовое возьмётся из таблицы.

Код ноутбука продублирован модулями в [`src/`](src/) — там же его удобнее читать.

## Структура

```
src/
  metric.py         MAP по группам кандидатов, векторизованный
  text.py           нормализация, свёртка азбук, починка гомоглифов
  features.py       58 парных признаков
  validation.py     GroupKFold по group_id + отчёт об утечке
  embeddings.py     rubert-tiny2 по уникальным текстам
  images.py         индекс фотографий, dhash, CLIP
  models.py         двухбашенная контрастная модель
  triplets.py       отбор трудных негативов и обучение башни на триплетах
  cross_encoder.py  дообучение трансформера на парах
  blend.py          смешивание предсказаний по рангам
  device.py         выбор устройства проверкой, а не флагом доступности
notebooks/          ноутбуки для Kaggle: основной и эксперимент с триплетами
reports/            results.json и results_triplet.json — полные выводы прогонов
```
